# رسانهٔ کلاس مجازی روی VPS Ubuntu 24.04

این مسیر مستقل از PersianMeet است. سایت PHP روی هاست اشتراکی می‌ماند؛ مرورگر سیگنال‌دهی را از Caddy با HTTPS/WSS و صدا را مستقیم با LiveKit انجام می‌دهد. سقف اولیهٔ پایلوت ۴ اتصال صوتی در هر اتاق است. Redis، Docker، TURN و ضبط در این پروفایل استفاده نمی‌شوند.

اگر LiveKit برای **همین سایت آزمایشی** از قبل فعال است، مراحل ۱ تا ۳ نصب تازه را تکرار نکن. فقط [وب‌هوک بومی LiveKit را روی VPS موجود ثبت کن](WEBHOOK-fa.md). نسخهٔ ۰٫۴٫۰ به ناظر جداگانه نیاز ندارد.

## ۱. دریافت فقط فایل‌های نصب از شاخهٔ آزمایش

روی VPS با SSH وارد شو. ابتدا Ubuntu را به‌روز نگه دار و اگر `git`، `curl`، Python 3 یا گواهی‌های ریشه موجود نیستند آن‌ها را نصب کن:

```bash
sudo apt update
sudo apt install git curl python3 ca-certificates
```

نسخهٔ نصب‌گر فقط از شاخهٔ کاری همین مخزن گرفته می‌شود. دریافت sparse از دانلود بستهٔ قدیمی PersianMeet جلوگیری می‌کند (درصورتی‌که سرویس Git قابلیت partial clone داشته باشد):

```bash
git clone --depth 1 --filter=blob:none --sparse --single-branch \
  --branch arena/a1a6c00e-bacirat-function \
  https://github.com/Maxess/bacirat-function.git school-media-pilot
git -C school-media-pilot sparse-checkout set server
cd school-media-pilot
```

## ۲. آماده‌سازی، بدون استارت یا تغییر فایروال

- `media.example.ir` در نمونه باید زیردامنهٔ اختصاصی VPS باشد و رکورد `A` به IPv4 عمومی سرور اشاره کند. دامنهٔ PHP هاست اشتراکی جداست. از پراکسی/CDN برای این زیردامنه در پایلوت استفاده نکن. `AAAA` را تنها وقتی بگذار که مسیر IPv6 و TLS را هم آزموده‌ای؛ رسانهٔ پایلوت با IPv4 تنظیم می‌شود.
- `X.X.X.X` را به IPv4 عمومی واقعی VPS و `https://test-school.example.ir` را به مبدأ دقیق **سایت تست** عوض کن. این مقادیر را در خود سرور وارد کن؛ نیازی به فرستادن آن‌ها در چت نیست.

```bash
sudo /usr/bin/python3 -I server/install.py media.example.ir X.X.X.X https://test-school.example.ir
```

نصب‌گر فایل رسمی Linux amd64 نسخهٔ `1.13.11` را دانلود و SHA-256 ثبت‌شده در GitHub را بررسی می‌کند. اگر دانلود دارایی GitHub روی VPS در دسترس نبود، همان [آرشیو رسمی LiveKit](https://github.com/livekit/livekit/releases/download/v1.13.11/livekit_1.13.11_linux_amd64.tar.gz) را از دستگاهی که دسترسی دارد منتقل کن و `--archive /path/to/livekit_1.13.11_linux_amd64.tar.gz` را به همان دستور اضافه کن؛ چک یکسان است. هیچ‌یک از فایل‌های پیکربندی موجود را جایگزین نمی‌کند و به SSH، apt، فایروال یا Caddy دست نمی‌زند. خروجی موفق `media_prepared=yes` است. برای تنظیم وب‌هوک در نصب تازه، طبق [راهنمای ثبت خودکار](WEBHOOK-fa.md#fresh-install) گزینهٔ `--webhook` را اضافه کن. اگر نصب قبلی وجود دارد، قبل از هر تغییر از پیکربندیِ خصوصی بکاپ بگیر؛ نصب‌گر از بازنویسی جلوگیری می‌کند.

## ۳. مسیر شبکه و HTTPS

| پورت | کاربرد |
| --- | --- |
| `443/TCP` | صفحهٔ PHP از طریق این آدرس WSS ویجت را وصل می‌کند و بک‌اند هاست آزمایشی هم فقط همین پورت را برای API می‌خواهد. |
| `80/TCP` | مسیر HTTP-01 وقتی Caddy گواهی از اینترنت می‌گیرد؛ دسترسی مرجع صدور لازم است. |
| `7882/UDP` | رسانهٔ WebRTC، یک پورت به‌جای یک بازه. در فایروال پنل و VPS برای شبکه‌های پایلوت مجاز شود. |
| `7881/TCP` | ICE/TCP اختیاری، اگر برای شبکهٔ آزمون لازم شد. این پورت HTTPS نیست. |
| `7880/TCP` و `7883/TCP` | داخلی و روی loopback؛ **در فایروال عمومی باز نشوند**. |

اگر پنل امکان محدودسازی دارد، مسیر رسانه را اول فقط برای شبکه‌های پایلوت باز کن. قواعد SSH یا سرویس‌های دیگر را تغییر نده. SSL سایت مدرسه جای گواهی معتبر سیگنال‌دهی روی زیردامنهٔ رسانه را نمی‌گیرد.

اگر Caddy روی VPS موجود نیست و وب‌سرور دیگری روی ۸۰/۴۴۳ فعال نیست، `sudo apt install caddy` بزن. اگر وب‌سرور دیگری داری، آن را بدون طرح جایگزین نکن. در Caddy موجود، ابتدا از `/etc/caddy/Caddyfile` بکاپ بگیر و این **یک خط** را با `sudoedit /etc/caddy/Caddyfile` در سطح اصلی اضافه کن؛ کل فایل را جایگزین نکن و از تکرار بلاک زیردامنه خودداری کن:

```caddyfile
import /etc/school-classroom/Caddyfile
```

سپس:

```bash
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl start school-classroom-admission school-classroom-sfu
sudo systemctl reload caddy
```

اگر گواهی صادر نشد، DNS و دسترسی بیرونی ۸۰/۴۴۳ را بررسی کن. اعتبارسنجی TLS را غیرفعال نکن. DNS-01 در صورت محدودیت ورودی HTTP مسیر دیگری است ولی نیاز به راه‌اندازی جداگانهٔ ارائه‌دهندهٔ DNS دارد؛ این نصب‌گر آن را خودکار نمی‌کند.

روی VPS وضعیت را بدون لاگ خصوصی گزارش کن:

```bash
sudo systemctl show school-classroom-sfu school-classroom-admission -p Id -p ActiveState -p Result
curl -fsS --max-time 8 https://media.example.ir/healthz
```

در صورت امکان `healthz` را از بیرون VPS هم امتحان کن. پاسخ سالم ۲۰۰ از مسیر HTTPS نشانهٔ دسترسی تا HTTP موتور است، **نه** اثبات کارکرد UDP و کیفیت صدا. اگر هر دو سرویس در پایلوت پایدار بودند می‌توانی `sudo systemctl enable school-classroom-admission school-classroom-sfu` بزنی. برای توقف پایلوت هر دو را متوقف و `import` همان سایت آزمایشی را از Caddy بردار؛ فایل کلیدها و دیتابیس اصلی مدرسه به هم وابسته نیستند.

## ۴. رویداد بومی LiveKit، بدون سرویس ناظر

برای نصب استاندارد و اختصاصی از [ثبت خودکار روی VPS](WEBHOOK-fa.md) استفاده کن. این روش به بارگذاری دوبارهٔ ZIP در سایت نیازی ندارد. راهنمای زیر برای ادغام دستی در پیکربندیِ اختصاصیِ سفارشی است.

<a id="manual-native-events"></a>
### ادغام دستی در LiveKit اختصاصی تست

- بستهٔ ۰٫۴٫۰ از همان LiveKit و درگاه صوتی موجود استفاده می‌کند. ناظر، اسکریپت پایش یا پورت جدید لازم نیست. در تب **تنظیمات دیگر ← افزونه‌ها** نشانی **گیرندهٔ وب‌هوک LiveKit** را بردار. اگر سایت در زیرپوشه است، خود URL نشان‌داده‌شده آن زیرمسیر را دارد.
- روی رسانهٔ **اختصاصی تست** از `/etc/school-classroom/livekit.yaml` بکاپ خصوصی بگیر. در زمان بیکاری کلاس، بلاک زیر را با `sudoedit` در فایل **ادغام** کن (کل فایل را بازنویسی نکن و `webhook` یا `api` تکراری نساز):

```yaml
webhook:
  api_key: KEY_ALREADY_CONFIGURED_FOR_THIS_TEST_SITE
  urls:
    - 'https://test-school.example.ir/school-test/plugins/school-plugins.php?plugin=school-classroom&route=events'
api:
  enable_psrpc_for_get_list_participants: true
```

مقدار `api_key` از بخش `keys` **همان** LiveKit و برابر API Key تنظیم‌شده در افزونه است. از API Secret در این بلاک یا در URL استفاده نکن. در بخش موجود `room`، گزینهٔ `auto_create: false` را حفظ کن؛ بلیتِ قدیمی نباید بتواند اتاق حذف‌شده را دوباره ایجاد کند. تنظیم `api` بالا خواندن فهرست حاضران را روی LiveKit نسخهٔ بررسی‌شده (`1.13.11`) به وضعیت زنده متصل می‌کند. اگر پیکربندی فعلی سفارشی/مشترک است، به‌جای اعمال روی سرویس‌های دیگر، نمونهٔ اختصاصی تست را جدا تنظیم کن.

- اگر از ۰٫۳٫۰ می‌آیی، **پس از پایان زنگ‌ها و تأیید غیرفعال‌سازی نسخهٔ قبلی**، فقط روی VPS اختصاصی تستی که آن سرویس را دارد، ناظر قدیمی را با `sudo systemctl disable --now school-classroom-watch` خاموش کن. درگاه `school-classroom-admission` و Caddy موجود را جایگزین نکن؛ درگاه قبلی، اتاق‌های نسخهٔ تازه را به‌عنوان اتاق‌های شنونده می‌پذیرد. فایل‌های پشتیبان قدیمی را برای بازگشت نگه دار.
- در روش دستی، تنظیم وب‌هوک را **بعد از پایان همهٔ زنگ‌ها و در زمان نگهداری** با `sudo systemctl restart school-classroom-sfu` روی همان VPS آزمایشی فعال کن. پیش از ورود دانش‌آموز، هم دسترسی HTTPS خروجی VPS به مدرسه و هم دسترسی HTTPS خروجی هاست به LiveKit را بررسی کن. وب‌سرور هاست باید هدر `Authorization` درخواست LiveKit را بدون بازنویسی به PHP بدهد و مسیر `route=events` را پشت ورود وب/چالش مرورگر نبرد؛ درخواست بدون امضا مجاز نیست. ساعت دو سرور درست باشد. وب‌هوک **LiveKit** ارتباطی به وب‌هوک **بله/تلگرام** ندارد.

### توقف، انتظار و محدودیت قطع ارتباط

آغاز دسترسی دانش‌آموز به دو چیز نیاز دارد: رویداد امضاشدهٔ LiveKit برای همان اتاق و اتصال فعالِ دبیر، مدیر یا ناظمِ مجاز با همان نشست سایت. با خروج آخرین مسئول، رویداد خروج یا بررسی وضعیت در درخواست‌های کلاس حذف اتاق را از API همان LiveKit انجام می‌دهد. اگر مسئول دیگری همچنان حاضر باشد اتاق باز می‌ماند. پس از بسته‌شدن، نسخهٔ تازهٔ اتاق با ورود مجدد مسئول ساخته می‌شود؛ این زمانِ انتظار در حضور حساب نمی‌شود.

اگر وب‌هوک نرسد، حالت درخواست‌های کلاس حذف/بستن را پیگیری می‌کند؛ وب‌هوک تأییدنشده اجازهٔ ورود دانش‌آموز به **اتاق جدید** نمی‌دهد. در قطع ارتباط، سایت با نمونهٔ کهنه بلیت تازه، چت یا تخته نمی‌دهد و مرورگرهای کلاس پس از تشخیص قطعی، از رسانه خارج می‌شوند. **اگر هم رویداد نرسد و هم هاست به API رسانه دسترسی نداشته باشد، قطع فوری یک جریان RTP برقرارشده از طرف PHP قابل تضمین نیست.** زمان تشخیص قطع به WebRTC، شبکه و رسیدن درخواست وابسته است. برای توقف قطعی فقط در **VPS اختصاصی تست**، در صورت نیاز `sudo systemctl stop school-classroom-sfu` کل رسانهٔ همان سرویس را قطع می‌کند.

### بررسی روی هاست تست

1. با حساب دانش‌آموز، دبیرِ همان زنگ، مدیر مجاز و ناظم در نشست‌های جدا منوی فعال و ورود مستقیم را بررسی کن. حساب کلاس دیگر و دانش‌آموز قبل از مسئول به رسانه، چت و تخته دسترسی نداشته باشند. اگر چند زنگ مجاز است، انتظار انتخاب زنگ طبیعی است.
2. با نوبت مجاز، اولین گوینده دانش‌آموز باشد، بدون اینکه میکروفون دبیر روشن شود. قطع تصویر، قطع میکروفون و گرفتن نوبت از همه مستقل باشند. یک تصویر، PDF چندصفحه‌ای، قلم، پاک‌کن و چت را روی دسکتاپ و موبایل امتحان کن.
3. خروج آخرین مسئول را هم با دکمهٔ خروج و هم با قطع اتصال آزمایش کن. دانش‌آموز به انتظار برگردد، بازگشت مسئول همان زنگ را در اتاق جدید با حفظ تخته و شمارنده‌ها ادامه دهد. با حضور یک مسئولِ دیگر زنگ قطع نشود. پایان کلاس باید گزارش همان زنگ را با مدت صفر برای غایب ثبت کند.
4. اعلان‌ها را ابتدا خاموش نگه دار. در صورت نیاز [تنظیم ارسال](../plugin-manager/README-fa.md#notices) را فقط برای حساب‌های کنترل‌شدهٔ تست بررسی کن. در ZIP سایت، این بخش در `README-fa.md` کنار پوشهٔ `media/` است.

سلامت HTTP، آزمون محلی با شبیه‌ساز یا یک بار شنیدن صدا، تأیید شبکهٔ گوشی، ICE، راه‌اندازی مجدد، پایداری و ظرفیت چند کلاس نیستند. برای گزارش مشکل فقط نسخه، نوع دستگاه، کد ثابت پیام و نتیجهٔ آزمون را بفرست؛ کلیدها، توکن، نشست و لاگ خصوصی را نفرست.
