# پایلوت خصوصی PersianMeet روی Ubuntu 24.04

**هدف این مرحله:** یک اتاق آزمایشی (یک دبیر و دو دانش‌آموز آزمایشی، ظرفیت تنظیم‌شدهٔ ۴ نفر) با صدا، تخته و چت. برای طراحی، خروجی حدود ۱۲ Mbps فرض شده؛ این عدد ظرفیت VPS را تأیید نمی‌کند. با داده و حساب آزمایشی شروع کن، نه اطلاعات دانش‌آموزان واقعی.

نصب‌گر یک نمونهٔ جداگانه در `/var/lib/persianmeet-pilot` آماده می‌کند. فایل‌های نرم‌افزار موجود در مخزن را تغییر نمی‌دهد. هش فایل ZIP ربط آن به همین نسخهٔ مخزن را بررسی می‌کند، نه اعتبار ناشر را؛ فقط اگر به منبع بسته اعتماد داری روی VPS اجرا کن.

## ۱. نصب و آزمون داخلی، بدون بازکردن پورت

ابتدا به‌روزرسانی‌های Ubuntu را نصب کن. به Python 3، systemd، `ip`، `unshare` و `curl` نیاز داریم؛ در Ubuntu 24.04 معمولاً موجودند. بسته‌ای را بدون نیاز نصب نکن.

دو فایل [`scripts/install-persianmeet-pilot.py`](../scripts/install-persianmeet-pilot.py) و `persianmeet-linux-v0.26.3.zip` را به پوشهٔ خانگی کاربر SSH منتقل کن. مثلاً از ترمینال کامپیوتری که این دو را در پوشهٔ جاری دارد، `SSH_USER` و زیردامنهٔ مثال را عوض کن:

```bash
scp install-persianmeet-pilot.py persianmeet-linux-v0.26.3.zip SSH_USER@class.example.ir:~/
```

روی VPS:

```bash
cd "$HOME"
sudo /usr/bin/python3 -I install-persianmeet-pilot.py persianmeet-linux-v0.26.3.zip
```

نصب‌گر بسته را با کاربر سیستمی جدا و در یک شبکهٔ ایزوله بالا می‌آورد، رمز مدیر پیش‌فرض را از مسیر عادی خود برنامه تغییر می‌دهد و رد شدن رمز قدیمی و تغییر نشست را بررسی می‌کند. اتاق نمونهٔ `/room/1` را به اتاق آزمایشی با دو رمز جداگانهٔ دبیر/دانش‌آموز تبدیل می‌کند. یک پایگاه SQLite تازه می‌سازد؛ روی نصب موجود بازنویسی نمی‌کند.

اگر خط `pilot_ready=yes` را دیدی، سرویس را به‌صورت خصوصی اجرا کن:

```bash
sudo systemctl start persianmeet-pilot
sudo systemctl show persianmeet-pilot -p ActiveState -p SubState -p Result
pid=$(sudo systemctl show -p MainPID --value persianmeet-pilot)
if [ "${pid:-0}" -gt 0 ]; then
  sudo nsenter -t "$pid" -n -- curl -fsS --retry 2 --retry-connrefused --retry-delay 1 --max-time 3 -o /dev/null -w 'room_http=%{http_code}\n' http://127.0.0.1:8003/room/1
  sudo nsenter -t "$pid" -n -- curl -sS --max-time 3 -o /dev/null -w 'sfu_no_token_http=%{http_code}\n' http://127.0.0.1:8003/sfu/rtc/validate
  ps -p "$pid" -o rss= | awk '{print "idle_rss_kib=" $1}'
fi
```

انتظار: `ActiveState=active`، `room_http=200`، `sfu_no_token_http=401`. مورد آخر عمداً **401** است؛ یعنی سیگنال‌دهی به درخواست بدون توکن اجازه نداده. این فقط سلامت وب و سیگنال‌دهی را بررسی می‌کند، نه جریان صوتی. در این حالت `PrivateNetwork=yes` است: نه Caddy میزبان به سرویس می‌رسد و نه اتاق از بیرون در دسترس است. نصاب فایروال و SSH را تغییر نمی‌دهد و سرویس را برای راه‌اندازی خودکار فعال نمی‌کند.

اطلاعات پنل و اتاق فقط در VPS و در دسترس root هستند. اگر لازم شد آن‌ها را **فقط خودت** بخوان:

```bash
sudo cat /var/lib/persianmeet-pilot/pilot-access.txt
```

**این فایل، `config.yml` تولید‌شده، پایگاه داده، یا خروجی کامل `journalctl` را نفرست.** برنامه بعضی کلیدهایش را در لاگ شروع چاپ می‌کند. برای گزارش نصب، فقط خط `pilot_ready`، دو کد HTTP و وضعیت سرویس را بفرست.

## ۲. دسترسی آزمایشی مرورگر از بیرون، پس از سلامت مرحلهٔ اول

این مرحله برای تعداد کمی آزمایش‌کننده است، نه انتشار عمومی. اگر فایروال پنل امکان محدودکردن IPها را ندارد یا دربارهٔ قواعد فعلی مطمئن نیستی، سرویس را در حالت خصوصی نگه دار. قبل از تغییر شبکه، در پنل و سیستم‌عامل، دسترسی غیرمجاز را هم برای IPv4 و هم IPv6 بررسی کن؛ حذف رکورد `AAAA` به‌تنهایی دسترسی مستقیم IPv6 را نمی‌بندد. هیچ تغییری در قانون SSH نده.

| پورت | نیاز و دامنهٔ دسترسی |
| --- | --- |
| `80/TCP` | برای صدور گواهی با HTTP-01 در صورت استفاده. مرجع صدور باید از اینترنت به آن دسترسی داشته باشد. |
| `443/TCP` | وب و WebSocket روی HTTPS؛ فقط اتصالات کاربران پایلوت به خود برنامه برسند. |
| `8003/TCP` و `7880/TCP` | برنامه و API داخلی SFU؛ **از اینترنت باز نشوند**. پروکسی روی همان VPS به `127.0.0.1:8003` وصل می‌شود. |
| `20000–30000/UDP` | بازهٔ ICE گزارش‌شده برای SFU داخلی همین بسته (LiveKit 1.13.11). برای تست مستقیم رسانه فقط به IPهای آزمایشی محدودش کن. |
| `7881/TCP` | مسیر اختیاری ICE/TCP، فقط در صورت نیاز و برای همان IPهای آزمایشی. |

ترتیب پیشنهادی:

1. **ابتدا فایروال**: پورت‌های داخلی بالا از بیرون بسته باشند و رسانه فقط برای IPهای آزمایش مجاز باشد. اگر پورت‌های برنامه روی VPS قبلاً اشغال‌اند، قبل از ادامه تداخل را حل کن. TURN داخلی در پروفایل پایلوت خاموش است؛ اگر UDP برقرار نشد، اول مسیر ICE، آدرس عمومی و فایروال را بررسی کن.
2. **HTTPS**: رکورد `A` زیردامنه باید مستقیماً به VPS برسد. اگر وب‌سرور دیگری نداری و ۸۰/۴۴۳ خالی‌اند، می‌توانی Caddy را از بسته‌های Ubuntu نصب کنی (`sudo apt install caddy`). این قطعه را به تنظیمات Caddy اضافه کن، نه اینکه تنظیم سایت‌های دیگر را جایگزین کنی. زیردامنه و IPهای مستنداتی مثال را **به مقادیر واقعی** تغییر بده. Caddy باید مستقیم ترافیک مبدأ را ببیند؛ این نمونه برای CDN یا پروکسی بیرونی طراحی نشده است.

   ```caddyfile
   class.example.ir {
       @pilot remote_ip 192.0.2.10/32 198.51.100.20/32
       handle @pilot {
           reverse_proxy 127.0.0.1:8003
       }
       handle {
           respond "Pilot access only" 403
       }
   }
   ```

   ```bash
   sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
   sudo systemctl reload caddy
   ```

   از همان شبکهٔ مجاز، گواهی را بدون خاموش‌کردن اعتبارسنجی مرورگر بررسی کن. تا وقتی سرویس خصوصی است، بعد از برقراری HTTPS خطای upstream (مثلاً 502) طبیعی است. اگر HTTP-01 ممکن نبود، روی گواهی DNS-01 به‌عنوان مرحلهٔ جداگانه کار می‌کنیم؛ آن روش ممکن است تنظیم یا ارائه‌دهندهٔ DNS جداگانه لازم داشته باشد.
3. **اتصال برنامه به فایروال و پروکسی آماده**: فقط بعد از دو مرحلهٔ بالا، `sudo systemctl edit persianmeet-pilot` را اجرا و این دو خط را در بخش ویرایش وارد کن:

   ```ini
   [Service]
   PrivateNetwork=no
   ```

   سپس `sudo systemctl restart persianmeet-pilot`. این تغییر باعث می‌شود برنامه در شبکهٔ میزبان گوش بدهد، پس بررسی مرحلهٔ فایروال ضروری است. وب و سیگنال‌دهی هر دو از همان HTTPS می‌گذرند؛ بسته خودش مسیر `/sfu` را دارد و برای مرورگر به بازکردن `7880/TCP` نیاز نیست. توقف فوری در صورت مشکل: `sudo systemctl stop persianmeet-pilot`. برای برگشت به حالت خصوصی، مقدار override را به `PrivateNetwork=yes` برگردان و سرویس را دوباره اجرا کن.
4. **ورود آزمایشی**: جهت ورود دبیر و دانش‌آموز، `https://<زیردامنه>/room/1` و رمز نقش درست را استفاده کن؛ `/dash/login` فقط برای مدیر است. نام‌ها و فایل‌های ساختگی استفاده کن.

## ۳. معیار پذیرش

- از دو شبکه، یک دبیر و دو دانش‌آموز آزمایشی با مرورگر وارد شوند. با رمز نامعتبر ورود موفق نشود. صدا را اول فقط با میکروفون دبیر بگیر؛ سپس آن را ببند و نوبت دانش‌آموز را امتحان کن. قطع مجوز باید در دستگاه‌های دریافت‌کننده واقعاً صدا را قطع کند.
- چت، دست‌بلندکردن، تصویر و PDF کوچک چندصفحه‌ای را جدا امتحان کن. همه از جمله کاربرِ واردشده با تأخیر باید صفحهٔ فعلی و نوشته‌های دبیر را ببینند. هنوز رفتار این قسمت‌ها با مرورگر بررسی نشده است.
- برای پروفایل ۱۲ Mbps، دوربین و اشتراک صفحه در این پایلوت استفاده نشوند. نصب‌گر مقدار سقف ویدئو را صفر می‌گذارد، ولی معنای آن در همهٔ مسیرهای انتشار و اجرای خودکار قانون «فقط یک گوینده» هنوز تأیید نشده است. **نوبت را دستی کنترل کن**؛ این آزمایش را معادل پیاده‌سازی محدودیت قطعی سمت سرور ندان.
- قبل از اضافه‌کردن اتاق دوم، یک جلسهٔ آزمایشی ۳۰ دقیقه‌ای برگزار و کیفیت صدا، اوج CPU و رم، و مسیر UDP/TCP را ثبت کن. سپس تازه به مرحلهٔ سه اتاق و بعد نه اتاق برس و بار هدف را بسنج.

نصب، تغییر رمز مدیر، ساخت اتاق و پاسخ ۲۰۰/۴۰۱ سرویس systemd در محیط آزمایشی بررسی شده‌اند. نه TLS روی زیردامنهٔ مدرسه و نه کیفیت صدای کاربران VPS هنوز سنجیده شده است.
